### Контекст и пользователи

HelpHealth разработан студентом(Белова О.И.), как индивидуальная курсовая работа первого года магистратуры. 
На текущем этапе продукт является учебным прототипом. Отдельных команд эксплуатации, QA, DevOps у проекта нет, а разработка и сопровождение выполнялись самостоятельно. Архитектурные и функциональные решения принимались в рамках целей курсовой работы.
Целевой контекст возможного применения - поликлиники, частные медицинские центры и телемедицинские сервисы. Пациент использует Android-приложение дома, в том числе между очными приёмами, а врач работает с данными через web-интерфейс. Особое внимание в работе уделено пожилым людям, пациентам с хроническими заболеваниями и жителям удалённых территорий.

HelpHealth предназначен для дистанционного наблюдения за состоянием пациентов из групп риска и для организации постоянного информационного взаимодействия между пациентом и врачом.

**Основные функции продукта:**
- регистрация и аутентификация пациентов и врачей
- привязка пациента к врачу по шестизначному коду
- получение и хранение показателей здоровья: пульса, SpO2, температуры, количества шагов, параметров сна и уровня стресса
- ручное ведение пациентом дневника самочувствия
- локальное хранение данных в Android-приложении и предусмотренная синхронизация с сервером
- загрузка медицинских документов, включая PDF-файлы с результатами лабораторных анализов
- извлечение структурированных показателей из лабораторных отчётов с помощью локального LLM/VLM-сервера
- просмотр врачом списка закреплённых пациентов, медицинских данных, дневника, документов и динамики показателей
- создание врачебных записей и рекомендаций для пациента
- уведомление врача об изменениях в данных пациента
- ведение записей на очный приём
- визуализация показателей и результатов анализов в web-интерфейсе

Результатом для пациента является единая точка ввода и просмотра данных о здоровье и получения рекомендаций врача. Врач получает централизованное представление динамики состояния своих пациентов между очными приемами.

**Пользователи**
- Пациент: регистрируется в Android-приложении, вводит данные дневника, передаёт показатели здоровья, загружает медицинские документы и читает записи врача
- Врач: работает через web-приложение, привязывает пациентов, просматривает их показатели и документы, анализирует динамику, создаёт записи и планирует приёмы

**Заинтересованные стороны**
- автор курсовой работы
- потенциальные медицинские организации и телемедицинские сервисы
- пациенты из групп риска и их лечащие врачи

### Границы

**В рассматриваемый объект входит:**
- Android-приложение пациента на Kotlin
- web-приложение врача на React
- backend API на Django REST Framework
- PostgreSQL
- модуль извлечения данных из PDF и интеграция с локальным OpenAI-совместимым API Ollama
- отправка писем подтверждения через SMTP
- Dockerfile, Docker Compose, Gunicorn и Nginx-конфигурация
- исходный код, конфигурация и учебная документация рассматриваемого снимка

**За пределами проекта остаётся:**
- фитнес-браслеты, умные часы и другие носимые устройства
- API и облачные экосистемы носимых устройств
- внутренняя реализация PostgreSQL, Docker, Nginx и иных сторонних компонентов; инфраструктура Yandex Cloud

**Обоснование границ:**
Границы охватывают программные компоненты, их данные, конфигурацию сборки и непосредственные точки интеграции. Реализация сторонних систем рассматривается как внешняя зависимость. Это позволяет воспроизводимо рассматривать код прототипа и выполнять улучшения, не включая недоступную инфраструктуру и не обрабатывая реальные данные пациентов.


### Компоненты, взаимодействия и границы доверия
**Основные компоненты**
1. Мобильное Android-приложение пациента

   Реализует регистрацию и вход, отображение показателей здоровья, дневник, загрузку документов и просмотр записей врача. Используется Retrofit/OkHttp для REST API и Room для локальных данных
2. Web-приложение врача

   React для регистрации и аутентификации врача, управления списком пациентов, просмотра медицинской карты, графиков, документов, уведомлений и записей на приём
3. Backend API

   Модульный монолит на Django REST Framework. Содержит бизнес-логику, REST эндпоинты, валидацию, разграничение ролей, обработку документов и создание уведомлений
4. PostgreSQL

   Хранит профили врачей и пациентов, связи между ними, диагнозы, показатели устройств, дневники, метаданные документов, результаты анализов, врачебные записи, уведомления и приёмы
5. Файловое хранилище

   Хранит загруженные документы и медиафайлы в volume приложения
6. Модуль обработки лабораторных PDF

   Извлекает текст из PDF с помощью `pdfplumber`, отправляет его локальному LLM/VLM-сервису, проверяет JSON-ответ и сопоставляет показатели со справочником анализов

7. Компоненты развёртывания

   Docker Compose, контейнер backend с Gunicorn, контейнер web-приложения с Nginx и контейнер PostgreSQL

**Внешние системы и сервисы**
- носимое устройство или любой другой источник показателей
- SMTP-сервис для отправки подтверждения электронной почты
- локально развёрнутый Ollama-сервер с OpenAI-совместимым API
- виртуальная машина для развёртывания
- Android-устройство пациента и браузер врача
- GitLab-репозиторий

- backend и хранилищами

**Границы доверия**
- Граница доверия 1

*Между:* устройством пациента или браузером врача и публичным интерфейсом HelpHealth

*Что пересекает границу:* учётные данные, токены, REST-запросы и ответы, показатели здоровья, дневниковые записи, документы и врачебные рекомендации

*Почему граница существенна:* пользовательские устройства и сеть не контролируются серверной частью; все входные данные должны считаться недоверенными, а соединение должно быть защищено

- Граница доверия 2

*Между:* ролью пациента, ролью врача и отношением привязки конкретного пациента к конкретному врачу

*Что пересекает границу:* идентификатор/код пациента, медицинские показатели, документы, записи и команды изменения данных

*Почему граница существенна:* данные пациента должны быть доступны только самому пациенту и уполномоченному врачу. Ошибка аутентификации, авторизации или фильтрации queryset может раскрыть либо изменить чужие медицинские данные

- Граница доверия 3

*Между:* backend API и PostgreSQL/файловым хранилищем.  

*Что пересекает границу:* персональные данные, медицинские показатели, документы, учётные данные, токены и служебные метаданные

*Почему граница существенна:* хранилища содержат основной массив чувствительных данных; важны аутентификация сервиса, минимальные привилегии, резервное копирование, шифрование и контроль доступа к volumes

- Граница доверия 4

*Между:* backend и локальным Ollama/VLM-сервисом

*Что пересекает границу:* извлечённый из лабораторного PDF текст и сформированный моделью JSON с медицинскими показателями

*Почему граница существенна:* мед.данные не должны покидать контур; результат модели требует проверки формата, значений и привязки к пациенту

- Граница доверия 5

*Между:** Android-приложением, локальным хранилищем устройства и источником показателей носимого устройства

*Что пересекает границу:* показатели здоровья, локальные записи, идентификатор пациента и токен сессии

*Почему граница существенна:* физическое устройство пациента находится вне контроля разработчика, данные могут быть подменены, утрачены или прочитаны при компрометации телефона

- Граница доверия 6

*Между:* средой разработки/исходным кодом и средой развёртывания 

*Что пересекает границу:* исходный код, зависимости, контейнерные образы, конфигурация

*Почему граница существенна:* в архиве отсутствует CI/CD и подтверждённая цепочка происхождения артефактов, ошибки или компрометация сборки могут попасть в развёрнутый экземпляр

### Активы и существенные риски

- **Актив:** медицинские данные и документы пациента.  
  **Что может произойти:** посторонний пользователь прочитает их по чужому идентификатору.  
  **Почему это существенно:** раскрываются диагнозы, анализы и личные сведения; нужны проверки доступа на сервере.

- **Актив:** показатели здоровья и врачебные записи.  
  **Что может произойти:** данные будут изменены другим пользователем или ошибочно извлечены из PDF.  
  **Почему это существенно:** врач получит недостоверную информацию; необходимо проверять владельца записи и результат обработки документа.

- **Актив:** пароли, токены и ключи сервисов.  
  **Что может произойти:** значения попадут в исходники, ответы API или журналы.  
  **Почему это существенно:** злоумышленник сможет действовать от имени пользователя или сервиса.

- **Актив:** доступность API и обработчика PDF.  
  **Что может произойти:** большой файл или множество заданий исчерпают ресурсы сервера.  
  **Почему это существенно:** пациенты и врачи потеряют доступ к системе; нужны ограничения размера и числа заданий.

## 2. Методологическая основа

**Основная рамка:** NIST SSDF 1.1, SP 800-218 (2022). [Источник](https://csrc.nist.gov/pubs/sp/800/218/final).  
**Дополнительные источники:** OWASP ASVS 5.0.0: требования к авторизации и защите данных API. [Источник](https://owasp.org/projects/asvs).

**Почему выбрана эта основа:** SSDF позволяет задать выполнимый процесс для двух участников: требования, проверку изменений, исправление и решение о выпуске. ASVS помогает проверить конкретные права врача и пациента.  
**Что ещё рассматривали:** OWASP SAMM — оценка зрелости шире задачи одного учебного выпуска; OWASP Top 10 — перечня рисков недостаточно для назначения ответственности и условий выпуска.

- **SSDF PO.1 — требования безопасности.** Применимо из-за обработки медицинских данных. Белова составляет правила доступа пациента и врача, Кокоева проверяет их полноту. Результат: для каждого медицинского ресурса определены разрешённые операции и случаи отказа.
- **SSDF PO.2 и PO.4 — ответственность и критерии проверок.** Белова отвечает за исправление API, Кокоева — за независимые тесты и конфигурацию. Изменение проверяет партнёр; выпуск разрешают обе участницы после обязательных проверок.
- **SSDF PW.7 и PW.8 — анализ кода и тестирование.** Для API нужны проверка обработчиков и запросы от разных пользователей. Результат: сохранены причина дефекта, тест и сравнение поведения до/после.
- **SSDF PW.9 и RV.2 — безопасные настройки и устранение проблем.** Кокоева проверяет секреты и параметры запуска, Белова повторяет проверку. Результат: секреты вынесены из кода, настройки считываются из окружения, замечания имеют решение и владельца.
- **ASVS 5.0.0, 8.2.2–8.2.3 — доступ к объектам и полям.** Белова ограничивает доступ собственным пациентом или активной связью с врачом и исключает секретные поля из ответов. Кокоева проверяет чужой ID, запрос без фильтра и вложенную выдачу пациента. Результат: чужие данные и секретные поля недоступны, разрешённые операции работают. [Требования ASVS](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x17-V8-Authorization.md).

## 3. Текущее состояние

Продукт разработан как индивидуальная курсовая; сведения о прежних review и проверках не предоставлены. В исходниках есть Dockerfile, Compose и скрипт `backend/docker-cmd.sh`, запускающий миграции, импорт справочников и Gunicorn. Найдены три шаблонных теста Android/React; тестов прав доступа backend нет. [Инвентаризация](evidence/inventory.json).

При импорте в GitHub секреты удалены из конфигурации, настройки вынесены в окружение, добавлены исключения для локальных файлов. Gitleaks не обнаружил секретов в подготовленной копии. Приложение не собиралось и не запускалось. [Выполненные проверки](evidence/publication-check.md).

В Android показатели генерируются через `MockGenerator`; работа с реальным браслетом не подтверждена. Модуль PDF отправляет модели извлечённый текст, а не изображение. [Исходные свидетельства](evidence/source-review.md).

### Существенные разрывы

- **Разрыв:** R1 — медицинские маршруты наследуют `AllowAny`, а выборки ряда обработчиков не ограничены пользователем.  
  **Почему важен:** возможен доступ к чужим данным. Простое включение `IsAuthenticated` не решает всё: Android использует `Token`, а глобально подключена JWT-аутентификация.  
  **Свидетельство:** `backend/backend/settings.py:111–119`, `backend/api/views.py:167–182, 311–454`; [E01](evidence/source-review.md#e01).  
  **Приоритет:** высокий.

- **Разрыв:** R2 — `PatientSerializer` включает все поля пациента, в том числе токен и поле хеша пароля.  
  **Почему важен:** секретные данные могут попасть в прямые и вложенные ответы API.  
  **Свидетельство:** `backend/api/serializers.py:119–133`, `backend/api/models.py:261–292`; [E02](evidence/source-review.md#e02).  
  **Приоритет:** высокий.

- **Разрыв:** R3 — Android использует HTTP и журналирование BODY; backend печатает результат анализа PDF.  
  **Почему важен:** медицинские данные могут раскрыться в сети и журналах.  
  **Свидетельство:** `NetworkModule.kt:15–24`, `backend/api/views.py:346–349`; [E04](evidence/source-review.md#e04).  
  **Приоритет:** высокий при сетевом использовании.

- **Разрыв:** R4 — проверки PDF находятся в сериализаторе, который не используется загрузкой; ответ LLM проверяется неполно.  
  **Почему важен:** возможны недопустимые файлы, перегрузка и сохранение неверных результатов.  
  **Свидетельство:** `backend/api/serializers.py:136–168`, `backend/api/views.py:283–363`, `backend/api/function/conv.py:69–79`; [E05](evidence/source-review.md#e05).  
  **Приоритет:** высокий для обработки документов.

- **Разрыв:** R5 — нет подтверждённых проверок изоляции пациентов и воспроизводимого запуска.  
  **Почему важен:** нельзя доказать исправление доступа и готовность выпуска.  
  **Свидетельство:** [шаблонные тесты](evidence/source-review.md#e07), [ограничения проверки запуска](evidence/publication-check.md).  
  **Приоритет:** высокий перед выпуском.

Секреты, найденные в исходном архиве, удалены из публикуемой копии; их отзыв владельцем не подтверждён. Свидетельства E01–E08 относятся к исходному снимку до публикационных изменений.

## 4. Целевой Secure SDLC

- **Обязательные практики:** зафиксировать версию и правила доступа; проверить изменения партнёром, секреты и настройки; выполнить тесты доступа; сохранить решение о выпуске. При изменении PDF добавляются проверки формата, размера и ответа модели; при сетевом размещении — HTTPS и выдачи файлов; при смене зависимостей — проверка известных уязвимостей.
- **Ответственные:** предлагается закрепить за Беловой правила доступа и исправление API, за Кокоевой — тесты, конфигурацию и проверку секретов. Каждая проверяет результат партнёра; решение о выпуске принимают обе.
- **Результаты:** правила доступа, commit изменения, команды и версии проверок, результаты до/после, список незакрытых проблем и решение о выпуске.
- **Контрольные точки:** до реализации согласованы права и тесты; до принятия изменения партнёр проверил код; до выпуска повторены тесты на том же commit. Не выполненная проверка не считается успешной. Чужой доступ и раскрытие секретов блокируют выпуск.
- **Исключения:** записываются риск, причина отсрочки, ограничение, ответственный и срок до следующего выпуска. Требуется согласие обеих участниц. Высокий риск не принимается для работающей функции: её отключают либо откладывают выпуск. При разногласии выпуск откладывается, вопрос о масштабе обсуждается с преподавателем.
- **Объём курса:** локальный стенд с синтетическими данными, исправление прав доступа и секретных полей, тесты двух пациентов и двух врачей, повтор партнёром. Предварительно — четыре недели по шесть часов на участника в неделю. Если стенд не готов за первую неделю, LLM заменяется заглушкой; полноценный CI/CD и работа с реальными устройствами откладываются.

## 5. Технологический профиль

Выбраны два метода: проверка доступа к медицинским данным и проверка конфигурации с поиском секретов. Инструменты можно уточнить после лекций 06–08.

### Метод 1: Проверка доступа к API

**Риск или свойство:** R1/R2 — чужие медицинские данные и секретные поля в ответах.  
**Цель:** разрешить пациенту только свои данные, врачу — данные пациентов с активной привязкой.  
**Область проверки:** права маршрутов, выборки объектов, запись владельца и сериализация пациента.  
**Этап жизненного цикла:** анализ кода, исправление, проверка перед выпуском.  
**Способ или инструмент и версия:** ручной анализ по ASVS 5.0.0; планируются тесты Django/DRF APIClient. В `backend/pyproject.toml` указаны Django 4.2.30 и DRF 3.14.  
**Ведущий участник:** Белова О.И. — правила и исправление.  
**Как партнёр проверит результат:** Кокоева выполнит запросы без входа, с чужим ID, с чужим владельцем и после архивации связи; затем проверит разрешённые действия.  
**Ожидаемые свидетельства:** тесты, ответы до/после, commit исправления и повтор партнёра.  
**Что метод не покрывает:** защиту телефона, сети и выдачу файлов в обход API.

### Метод 2: Проверка конфигурации и секретов

**Риск или свойство:** секреты в исходниках и несогласованные настройки приложения и Compose.  
**Цель:** исключить встроенные секреты и проверить чтение настроек из окружения.  
**Область проверки:** settings, Compose, файлы окружения, публикуемые файлы и Git-история.  
**Этап жизненного цикла:** подготовка среды, проверка изменений и публикация.  
**Способ или инструмент и версия:** Gitleaks 8.30.1 со [стандартными правилами](evidence/gitleaks-default.toml); проверка settings на Python 3.14.5.  
**Ведущий участник:** Кокоева М.Р. — конфигурация и повторяемый протокол проверки.  
**Как партнёр проверит результат:** Белова повторит команды и проверит реальные значения настроек на тестовом окружении.  
**Ожидаемые свидетельства:** отчёты сканера, настройки без секретов, результат загрузки settings и подтверждение отзыва прежних секретов владельцем.  
**Что метод не покрывает:** действительность и отзыв секретов, права API и полноценный запуск приложения.

## 6. Практическая апробация

**Метод 1.** Проверены цепочки URL → viewset → serializer → model: требования входа, ограничение выборок и поля ответа. Использованы чтение кода и ripgrep 15.2.0. ```

Выходной каталог должен находиться вне исходников. Для изменённого кода диапазоны строк нужно пересмотреть.

- **R1/R2 — подтверждены по коду:** общий доступ `AllowAny`, неограниченные выборки и секретные поля пациента. Блокируют выпуск медицинского API; сетевое воспроизведение ещё требуется. [E01](evidence/source-review.md#e01), [E02](evidence/source-review.md#e02).

## 9. Решение о выпуске

**Решение:** отложить выпуск  
**Основания:** [разрывы доступа](evidence/source-review.md#e01), [секретные поля пациента](evidence/source-review.md#e02), [отсутствие подтверждённого запуска](evidence/publication-check.md).  
**Блокирующие проблемы:** есть: R1/R2 и отсутствие успешных обязательных проверок; R3/R4 блокируют соответствующие сетевые и документные сценарии.  
**Остаточные риски:** локальное хранение Android, обработка PDF, точность LLM, зависимости и восстановление данных проверены не полностью.  
**Условия, исключения и ответственные:** Белова исправляет доступ, Кокоева проверяет чужие и разрешённые операции; обе подтверждают запуск и результаты. Владелец отзывает прежние секреты. Непроверенную функцию отключают или откладывают выпуск; исключений для чужого доступа нет.

Выявленных разрывов достаточно, чтобы отложить выпуск. Для разрешения выпуска нужны проверки исправленного приложения; статический анализ и поиск секретов их не заменяют.

## 10. Метрики и программа развития

- **Метрики:** доля успешно выполненных обязательных тестов доступа — цель 100%; открытые высокие риски включённых функций — цель 0; успешный повтор запуска и проверок партнёром — обязателен для каждого кандидата. Сейчас тесты доступа и запуск не выполнены.
- **Ближайшие 2–4 недели, высокий приоритет:** Белова исправляет R1/R2, Кокоева готовит стенд и тесты. Результат — чужой доступ запрещён, законный работает, результаты сохранены.
- **1–3 месяца, высокий приоритет:** Белова добавляет защищённую выдачу файлов и проверку результата LLM; Кокоева проверяет размер, формат, тайм-аут и неверный JSON. Результат — контролируемый отказ без чужих или ошибочных данных.
- **3–6 месяцев, средний приоритет:** Кокоева автоматизирует уже работающие проверки и анализ зависимостей; Белова проверяет совместимость. Результат — повторяемая проверка каждого изменения.
- **6–12 месяцев, при продолжении проекта:** Белова проверяет хранение и очистку данных Android, Кокоева — резервное восстановление. Результат — воспроизводимые сценарии выхода, удаления локальных данных и восстановления стенда.

## 11. Управленческая записка

HelpHealth — учебный прототип для обмена медицинскими данными между пациентом и врачом. Для `release-v1` рассматриваются Android, web, API, БД и обработка документов. Проверки планируются на локальном стенде с синтетическими данными.

Выполнен статический анализ исходников и конфигурации. Найдены разрывы доступа к медицинским объектам, включение секретных полей в ответы пациента, HTTP и неполная проверка PDF/LLM-потока. Сборка и работающий API не проверялись.

Перед публикацией секреты удалены из кода, настройки вынесены в окружение. Повторный поиск известных значений и Gitleaks не обнаружили их в опубликованной копии. Это улучшение не устраняет проблемы авторизации; прежние секреты должен отозвать владелец.

Предлагается отложить выпуск. Ближайший результат курса — исправление доступа Беловой и независимые тесты Кокоевой. Выпуск возможен после успешного повторения обязательных проверок на одной версии; каждый участник должен подтвердить и объяснить свой вклад.
