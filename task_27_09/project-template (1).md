### Контекст и пользователи

HelpHealth разработан студентом(Белова О.И.), как индивидуальная курсовая работа первого года магистратуры. 
На текущем этапе продукт является учебным прототипом. Отдельных команд эксплуатации, QA, DevOps у проекта нет, а разработка и сопровождение выполнялись самостоятельно. Архитектурные и функциональные решения принимались в рамках целей курсовой работы.
Целевой контекст возможного применения - поликлиники, частные медицинские центры и телемедицинские сервисы. Пациент использует Android-приложение дома, в том числе между очными приёмами, а врач работает с данными через web-интерфейс. Особое внимание в работе уделено пожилым людям, пациентам с хроническими заболеваниями и жителям удалённых территорий.

HelpHealth предназначен для дистанционного наблюдения за состоянием пациентов из групп риска и для организации постоянного информационного взаимодействия между пациентом и врачом.

**Основные функции продукта:**
- регистрация и аутентификация пациентов и врачей
- привязка пациента к врачу по шестизначному коду
- получение и хранение показателей здоровья: пульса, SpO2, температуры, количества шагов, параметров сна и уровня стресса
- ручное ведение пациентом дневника самочувствия
- локальное хранение данных в Android-приложении и предусмотренная синхронизация с сервером
- загрузка медицинских документов, включая PDF-файлы с результатами лабораторных анализов
- извлечение структурированных показателей из лабораторных отчётов с помощью локального LLM/VLM-сервера
- просмотр врачом списка закреплённых пациентов, медицинских данных, дневника, документов и динамики показателей
- создание врачебных записей и рекомендаций для пациента
- уведомление врача об изменениях в данных пациента
- ведение записей на очный приём
- визуализация показателей и результатов анализов в web-интерфейсе

Результатом для пациента является единая точка ввода и просмотра данных о здоровье и получения рекомендаций врача. Врач получает централизованное представление динамики состояния своих пациентов между очными приемами.

**Пользователи**
- Пациент: регистрируется в Android-приложении, вводит данные дневника, передаёт показатели здоровья, загружает медицинские документы и читает записи врача
- Врач: работает через web-приложение, привязывает пациентов, просматривает их показатели и документы, анализирует динамику, создаёт записи и планирует приёмы

**Заинтересованные стороны**
- автор курсовой работы
- потенциальные медицинские организации и телемедицинские сервисы
- пациенты из групп риска и их лечащие врачи

### Границы

**В рассматриваемый объект входит:**
- Android-приложение пациента на Kotlin
- web-приложение врача на React
- backend API на Django REST Framework
- PostgreSQL
- модуль извлечения данных из PDF и интеграция с локальным OpenAI-совместимым API Ollama
- отправка писем подтверждения через SMTP
- Dockerfile, Docker Compose, Gunicorn и Nginx-конфигурация
- исходный код, конфигурация и учебная документация рассматриваемого снимка

**За пределами проекта остаётся:**
- фитнес-браслеты, умные часы и другие носимые устройства
- API и облачные экосистемы носимых устройств
- внутренняя реализация PostgreSQL, Docker, Nginx и иных сторонних компонентов; инфраструктура Yandex Cloud
- production-данные, реальные медицинские документы и рабочие учётные записи пациентов
- CI/CD-инфраструктура

**Обоснование границ:**
Границы охватывают программные компоненты, их данные, конфигурацию сборки и непосредственные точки интеграции. Реализация сторонних систем рассматривается как внешняя зависимость. Это позволяет воспроизводимо рассматривать код прототипа и выполнять улучшения, не включая недоступную инфраструктуру и не обрабатывая реальные данные пациентов.


### Компоненты, взаимодействия и границы доверия
**Основные компоненты**
1. Мобильное Android-приложение пациента

   Реализует регистрацию и вход, отображение показателей здоровья, дневник, загрузку документов и просмотр записей врача. Используется Retrofit/OkHttp для REST API и Room для локальных данных
2. Web-приложение врача

   React для регистрации и аутентификации врача, управления списком пациентов, просмотра медицинской карты, графиков, документов, уведомлений и записей на приём
3. Backend API

   Модульный монолит на Django REST Framework. Содержит бизнес-логику, REST эндпоинты, валидацию, разграничение ролей, обработку документов и создание уведомлений
4. PostgreSQL

   Хранит профили врачей и пациентов, связи между ними, диагнозы, показатели устройств, дневники, метаданные документов, результаты анализов, врачебные записи, уведомления и приёмы
5. Файловое хранилище

   Хранит загруженные документы и медиафайлы в volume приложения
6. Модуль обработки лабораторных PDF

   Извлекает текст из PDF с помощью `pdfplumber`, отправляет его локальному LLM/VLM-сервису, проверяет JSON-ответ и сопоставляет показатели со справочником анализов

7. Компоненты развёртывания

   Docker Compose, контейнер backend с Gunicorn, контейнер web-приложения с Nginx и контейнер PostgreSQL

**Внешние системы и сервисы**
- носимое устройство или любой другой источник показателей
- SMTP-сервис для отправки подтверждения электронной почты
- локально развёрнутый Ollama-сервер с OpenAI-совместимым API
- виртуальная машина для развёртывания
- Android-устройство пациента и браузер врача
- GitLab-репозиторий

**Существенные границы доверия проходят между**
- пользовательскими устройствами и API
- ролями врача и пациента
- backend и хранилищами
- backend и внешними SMTP и VLM-сервисами.

**Границы доверия**
- Граница доверия 1

*Между:* устройством пациента или браузером врача и публичным интерфейсом HelpHealth

*Что пересекает границу:* учётные данные, токены, REST-запросы и ответы, показатели здоровья, дневниковые записи, документы и врачебные рекомендации

*Почему граница существенна:* пользовательские устройства и сеть не контролируются серверной частью; все входные данные должны считаться недоверенными, а соединение должно быть защищено

- Граница доверия 2

*Между:* ролью пациента, ролью врача и отношением привязки конкретного пациента к конкретному врачу

*Что пересекает границу:* идентификатор/код пациента, медицинские показатели, документы, записи и команды изменения данных

*Почему граница существенна:* данные пациента должны быть доступны только самому пациенту и уполномоченному врачу. Ошибка аутентификации, авторизации или фильтрации queryset может раскрыть либо изменить чужие медицинские данные

- Граница доверия 3

*Между:* backend API и PostgreSQL/файловым хранилищем.  

*Что пересекает границу:* персональные данные, медицинские показатели, документы, учётные данные, токены и служебные метаданные

*Почему граница существенна:* хранилища содержат основной массив чувствительных данных; важны аутентификация сервиса, минимальные привилегии, резервное копирование, шифрование и контроль доступа к volumes

- Граница доверия 4

*Между:* backend и локальным Ollama/VLM-сервисом

*Что пересекает границу:* извлечённый из лабораторного PDF текст и сформированный моделью JSON с медицинскими показателями

*Почему граница существенна:* мед.данные не должны покидать контур; результат модели требует проверки формата, значений и привязки к пациенту

- Граница доверия 5

*Между:** Android-приложением, локальным хранилищем устройства и источником показателей носимого устройства

*Что пересекает границу:* показатели здоровья, локальные записи, идентификатор пациента и токен сессии

*Почему граница существенна:* физическое устройство пациента находится вне контроля разработчика, данные могут быть подменены, утрачены или прочитаны при компрометации телефона

- Граница доверия 6

*Между:* средой разработки/исходным кодом и средой развёртывания 

*Что пересекает границу:* исходный код, зависимости, контейнерные образы, конфигурация

*Почему граница существенна:* в архиве отсутствует CI/CD и подтверждённая цепочка происхождения артефактов, ошибки или компрометация сборки могут попасть в развёрнутый экземпляр
